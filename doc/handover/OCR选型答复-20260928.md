# 拍照识别（OCR）选型答复（2026-09-28）

> 起因：Kevin 问「拍照识别微信小程序有对应的 API 吗」。本文回答该问题，并给出本项目可落地的选型与待办。
> 与 `待拍板口径单-20260927.md` §二.1 是同一条：本文件是该条的**技术核实结果**，口径仍由 Kevin 拍。

## 一、结论（先看这五行）

1. **有。** 微信自己就提供 OCR 接口，小程序能调；但它**偏印刷体**（通用印刷体 + 身份证/银行卡/营业执照/行驶证/驾驶证/菜单），**没有手写体专项**。
2. **微信 OCR 从 2020-04-01 起全面计费**，免费额度统一为 **100 次/天**，超了要买资源包（所有调用方式共用同一份额度）。
3. 本项目合同第 2 行的样本标签是**手写为主**（甲方原始材料里要求「≥3 张手写」的样本照片），所以微信 OCR 的**通用印刷体**接口在准确率上不是最优解。
4. **腾讯云 OCR 更合适**：`通用印刷体识别` 与 `通用手写体识别` **各 1000 次/月免费、当月有效、每月自动发放**，正好覆盖「印刷 + 手写」两类样本，且额度对试用期足够。
5. 本项目的识别器**是可插拔的**，但要说准确：插槽、工厂、启动护栏、选择口径的单测**都已就位**（`OcrProvider` / `OcrProviderFactory` / `OcrProviderGuard` / `OcrProviderSelectionTest`，ADR-0007），**缺的是那一个适配器实现类**。所以接服务的真实工作量 = **写一个 provider 适配器（实现 `recognize`，标 `PaidOcrProvider`）+ 密钥配置**，不改业务代码、不动已验过的链路。

## 二、两条路的具体对比

| | 微信 OCR（服务市场） | 腾讯云 OCR |
|---|---|---|
| 接口 | `/cv/ocr/comm`（通用印刷体）、`/cv/ocr/idcard`、`/cv/ocr/bankcard`、`/cv/ocr/bizlicense`、`/cv/ocr/driving`、`/cv/ocr/drivinglicense`、`/cv/ocr/menu` | `GeneralBasicOCR`（通用印刷体）、`GeneralAccurateOCR`（高精度）、`GeneralHandwritingOCR`（**通用手写体**）、`TableOCR`（表格）等 |
| 小程序怎么调 | 服务市场 `wx.serviceMarket.invokeService`，或插件方式；也可后端代调（本项目走的就是后端代调） | 后端用 SDK / HTTPS 直调（与小程序无关，更适合本项目「照片先上传、后端识别」的链路） |
| **手写体** | ❌ 无专项接口（通用印刷体对手写弱） | ✅ **有专项**（`通用手写体识别`） |
| 免费额度 | **100 次/天**，所有调用方式共用；超出需买资源包 | `通用印刷体识别` **1000 次/月**、`通用手写体识别` **1000 次/月**，**当月有效、每月 1 号自动发放**；同账号多接口可能共享同一资源包 |
| 计费起点 | 2020-04-01 起全面计费 | 首次开通后自动发免费资源包（说明：账号 1 年未使用会暂停发放，再用时 2 分钟内自动下发） |
| 对本项目的适配度 | 可用，但手写样本上风险高 | **推荐**：手写/印刷各 1000 次/月，试用期绰绰有余 |

## 三、本项目的现状（代码事实，可复核）

| 事实 | 位置 / 取值 |
|---|---|
| 识别器是可插拔接口，默认实现是「不可用」 | `ocr/provider/OcrProvider.java`、`NoneOcrProvider.java`；决策记录 `doc/_adr/0007-ocr-pluggable-provider.md` |
| 已有两个实现：`none`（默认）与 `stub`（测试桩，用 `X-Ocr-Stub-Case` 头喂用例） | `NoneOcrProvider` / `StubOcrProvider`（`OcrProviderFactory` 按 bean 名解析） |
| 「按次收费」是一类**标记接口**，不是配置字符串 | `PaidOcrProvider extends OcrProvider`（**本身不含新方法**；真实 provider 要实现它才会被付费开关管住） |
| 三个配置键 | `lqg.ocr.provider`（默认 `none`）、`lqg.ocr.paid-enabled`（默认 `false`）、`lqg.ocr.max-bytes`（默认 5MB）；**每次请求现选**，改了下一次调用即生效 |
| 选择口径是纯函数 + 有单测 | `OcrProviderGuard.select(...)` / `OcrProviderSelectionTest` |
| 生产/试用环境当前不接外部服务，界面提示「识别不可用，请手动填写」 | 同上 |
| 识别结果 → 表单字段的**解析器**已按要求修好（原 `#203`，已结案） | 台账 `#203` |
| 结果回填链路已通：照片上传 → 后端调 provider → 字段回填 | `OCR-MP-001`、`OCR-EXT-001` 等票，均在新基线里绿 |

**所以要接腾讯云，具体是这么一步**（我可以做）：新增 `TencentOcrProvider implements PaidOcrProvider`（bean 名如 `tencent`），按样本类型或先印后手分别调 `GeneralBasicOCR` / `GeneralHandwritingOCR`，AK/SK 走环境变量；然后把 `lqg.ocr.provider=tencent`、`lqg.ocr.paid-enabled=true` 配上去，用甲方真实样本跑一遍留证。**不需要改任何已验收的业务代码。**

## 四、需要 Kevin 给的（二选一即可开工）

**选 A（推荐，腾讯云）**：给我一组腾讯云 OCR 的 `SecretId` / `SecretKey`（子账号即可，只需 OCR 只读调用权限）。
- 我做的事：写 `TencentOcrProvider`（印刷走 `GeneralBasicOCR`、手写走 `GeneralHandwritingOCR`，按样本类型或先印后手自动切换）→ 配 `lqg.ocr.provider=tencent` + `lqg.ocr.paid-enabled=true` → 用甲方真实样本跑一遍准确率留证。
- 免费额度下**不产生费用**（除非某月超过 2000 次调用）。

**选 B（微信自有）**：用小程序服务市场开通「微信 OCR 识别」。
- 优点：不用额外云账号。
- 代价：100 次/天、无手写专项；试用期演示够用，正式用会很快耗尽。

**无论选哪个，都建议同时做的一件事**：向甲方要**10 张以上真实样本照片（其中至少 3 张手写）**——这是合同第 2 行验收的判据素材，也是选 A 时验证准确率的输入。这条在 `待拍板口径单-20260927.md` §二.1 里已经写过。

**兜底**：若短期内拿不到密钥，就按口径单里的 **b** 方案——书面告知甲方「试用期先手填」，合同第 2 行挂账，不挡本地试用。
