## 1. 结论

不能按「38 张票完成、D1 到 D7 全部过门」直接验收，也还不能交给甲方试用。

代码主体是真做了，质量不差：

必须先处理的有四类：

1. **主流程数据错与信息泄露**：活体证实 5 条 S1。外部从小程序提交的组织样本丢了来源单位，工作台按单位筛选和导出都漏掉它们；核验抽屉里改的送检信息点保存被静默丢弃；外部接口缺字段时把 SQL 和整行数据回吐给外部；撤回一份文档后合并质控报告出错且界面修不回来；附件实际只能传两三兆，契约写的是 50MB。

3. **小程序没在微信里跑过**：验收全在 H5 上做。生产包的接口地址指向本机回环地址，协议和隐私政策是露着内部票号的占位页。

## 6. 部署改造方案

### 6.1 结论

可以照 dongjiaoshan 的模式改：推 staging 分支自动部署测试环境，推 main 分支自动部署生产，由 GitHub Actions 执行。执行方在 D8 写的生产 compose、nginx、证书续期、healthcheck、oss-init 与部署运维手册都能直接复用，只把「在本机构建、rsync 上机」这一步换成 CI。

### 6.2 与 dongjiaoshan 的对照

| 项 | dongjiaoshan | jiangxia 建议 | 理由 |
|---|---|---|---|
| 仓库 | 每端一个仓库 | 单仓推上去，workflow 按路径触发 | 票面、权威、验证脚本都按单仓路径写；后端构建还依赖 `doc/` 与 `_input/` 里的文件 |
| 触发 | push staging 与 main，外加手动 | 相同 | |
| 后端构建 | 服务器上 git reset 后在 Docker 里跑 Maven | GitHub 机器上打 jar 并跑单测，rsync 差量传上机，服务器只把 jar 装进薄镜像 | 测试机与 guzi、tianda 共用，可用内存约 2.9GB、磁盘余 14GB，在上面跑 Maven 有挤爆别人服务的风险；jar 有 175MB，差量传只传变动部分 |
| 工作台 | GitHub 机器构建，scp 到宝塔站点目录 | 相同，目标是 compose 里 nginx 的静态目录 | 现有环境就是这个分层 |
| 小程序 | GitHub 机器构建，miniprogram-ci 上传；robot 1 对 main，robot 2 对 staging | 相同 | 前提见 6.4 |
| 服务器 .env | 只在服务器 | 相同 | |
| 部署后自检 | 端口有响应就算成功，永远 exit 0 | 核镜像标签等于本次提交号、容器 healthy，不符就让任务失败 | 票面靠提交号防旧包 |
| 字典缓存 | 部署后刷 Redis 字典缓存 | 相同 | Flyway 直接改字典表会绕过缓存失效 |
| 生产前备份 | 无 | main 部署前先 pg_dump 一份 | Flyway 迁移不可逆，生产库与应用同机 |
| 人工闸 | 本地 ops/deploy.sh 加 --yes 才触发 prod | 相同，合进 main 本身就是闸 | |

### 6.3 分支

- main 对生产，staging 对测试环境。日常在功能分支开发，合进 staging 在测试环境验，验过再合进 main。
- 过渡：现在 integration 就是最新代码。从 integration 切出 staging 推上去；main 目前只有初始化提交，等生产服务器到位再合。task/D1 到 task/D8 留在本地作历史。
- 推 staging 不自动 reseed。测试环境是甲方试用的地方，reseed 只能手动触发，workflow_dispatch 带一个开关。
