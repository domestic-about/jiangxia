## 4. 回答你的问题：白名单为什么是服务器的 IP？代码从哪发？

**现在代码是从测试机（`118.178.109.11`）发给微信的 —— 不是 GitHub Actions。这是我这一轮改的，理由如下。**

原来的方式（也是项目的原始设计）：在**开发机**上构建 + 上传。但微信要求上传来源 IP 在白名单里，而我这台开发机常年跑在代理后面 ——
实测 `curl --noproxy '*'` 与直连拿到的是**同一个**代理出口 IP（`160.16.223.125`，TUN 层劫持，按进程绕不过去）。
那个 IP 不稳定、也不该长期占白名单。所以我把上传挪到了固定公网 IP 的测试机：

```
开发机（macOS）构建  →  同步产物  →  测试机（固定 IP 118.178.109.11）上传  →  微信
```

- **构建必须留在开发机**：项目纪律（栈包 gotchas §6.5）—— 不同 OS 产物不同，体验版真机上会渲染空。
- 上传脚本自带的**两道发布守卫**（appid 格式 / https / 非回环内网 / mock 痕迹 / 接口地址真的打进包）在开发机与测试机**各跑一遍**。
- 上传成功后自动出**体验版二维码**并回传到你本机 `code/miniapp/dist/`（已 gitignore）。

**那 GitHub Actions 行不行？** 行，但要绕两个坑，而且**现在还谈不上**（这个仓库连远端都没配）：

| 方案 | 固定 IP？ | 构建 OS | 评价 |
|---|---|---|---|
| **A. 测试机上传（现在这样）** | ✅ 固定 `118.178.109.11`，加一次长期有效 | 开发机 macOS ✅ | 今天就能用，零额外基建 |
| B. GitHub Actions（托管 runner） | ❌ 每次 IP 不同，官方只给 IP 段不给固定 IP → **白名单根本没法配** | Linux runner ❌（产物会让真机渲染空） | 除非改用自托管 runner 或走固定出口代理 |
| C. GitHub Actions + **自托管 runner 装在测试机上** | ✅ 固定 | 仍是 Linux ❌ | 只解决 IP，不解决构建 OS |
| D. Actions 用 **macOS runner 构建** → 把产物丢给测试机 → 测试机上传 | ✅ 固定 | macOS ✅ | **要上 CI 的话这是正解**：构建在 macOS runner、上传复用现在这条服务器路径 |

所以：
- **今天**用 A（已建好，`bash code/deploy/test/deploy.sh miniapp`）。
- **将来要 CI** 就走 D：GitHub Actions 的 macOS runner 负责构建，产物 rsync 到测试机，再触发测试机上的上传。
  这需要你先定口径：仓库放个人账号还是新建组织、`doc/` 是否一起推、CI 用哪把 SSH 密钥登测试机（就是独立验收报告 §6.7 那四问）。
