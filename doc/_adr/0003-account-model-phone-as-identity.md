# ADR-0003: 账号模型——一套账号，手机号定身份

**决策者**: 待 Kevin 过目（AI 依据会议口径给出的实现模型）
**关联**: REQ-AUTH-001 / 002 / 003 / 004 / 008 / 010、FLOW:F-AUTH-01、FLOW:F-AUTH-02、t_lqg_wx_bind、t_lqg_ext_profile

## 背景

会上定的业务口径（逐字稿 L238-L295）：都是微信登录 + 授权手机号；内部人员由实验室在网页端按手机号挂角色；外部不设准入；
内外部「最好是按照人」来区分，不能让用户自己选，否则外部的人会想看内部的信息。

## 决策

按 frontmatter。三个会做错的点：

1. **授权是升级不是新建**。实验室给一个手机号授权时，这个人很可能已经用小程序登录过（当时是外部）。此时再新建一个内部账号，
   同一个手机号就有两个账号，下次登录命中哪个全看查询顺序。所以按手机号授权 = 找到就改角色，找不到才预建。
2. **样本的内外部属性是提交当时的快照**（REQ-SAMPLE-009），不跟着账号升降级变。
3. **工作台拒绝外部角色是后端行为**：登录接口按角色拒绝，不是登录成功后前端没菜单。

「内外部分成两张用户表、两套登录」不采纳：token、权限注解、审计字段全要写两套。
「让用户登录时自选内部或外部」不采纳：甲方 L88 明确反对。
「外部用户须实验室预先开通才能登录」不采纳：会上讨论过后否决（L277 来了新员工还得重新挂载，L295 定为不限制）。

## 后果

- 小程序登录接口返回身份（internal / external），首页按身份渲染入口（REQ-AUTH-014）。
- 手机号是关键标识：同一手机号换微信号登录 → 绑定表多一行 openid，仍是同一个账号。
- 撤销内部授权 = 角色改回 lqg_external 并踢下线；此人以前以内部身份录的样本仍是内部样本。
